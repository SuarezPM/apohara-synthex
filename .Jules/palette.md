## 2026-05-29 - Adding Form Usability to Live Console\n**Learning:** The live console in public/index.html was not wrapped in a formal <form> tag, which meant natural keyboard navigation (pressing Enter to submit) didn't work. The input also lacked guidance (placeholder) and validation (empty submissions were allowed), leading to a frustrating experience. Adding aria-busy to the submit button provides critical screen-reader feedback during the long-running async pipeline execution.\n**Action:** When working with custom JS-driven "forms" that don't use standard HTML <form> submission, always ensure keyboard events (keydown Enter) are manually wired to trigger the primary action, and manage aria-busy state on buttons for async operations.
## 2026-06-19 - Managing Disabled States on Interactive Elements with Existing Hover Styles
**Learning:** Adding a `:disabled` attribute/state to a button element isn't enough if there are existing `:hover` styles defined on the button's class. The `:hover` styles can incorrectly override the disabled visual state, causing a "disabled" button to still look interactive when hovered over, which degrades the UX. Additionally, for long-running async actions triggered by the button (e.g. generating a PDF), failing to show a loading state leaves the user without feedback.
**Action:** When adding disabled states to UI elements in the frontend, always review and update existing hover effects (e.g. changing `.btn:hover` to `.btn:not(:disabled):hover`). For async operations, manage the loading state using `try...finally` to ensure robust state restoration (e.g., setting `disabled=true`, `aria-busy="true"`, and providing textual/visual feedback).
