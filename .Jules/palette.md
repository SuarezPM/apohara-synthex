## 2026-05-29 - Adding Form Usability to Live Console\n**Learning:** The live console in public/index.html was not wrapped in a formal <form> tag, which meant natural keyboard navigation (pressing Enter to submit) didn't work. The input also lacked guidance (placeholder) and validation (empty submissions were allowed), leading to a frustrating experience. Adding aria-busy to the submit button provides critical screen-reader feedback during the long-running async pipeline execution.\n**Action:** When working with custom JS-driven "forms" that don't use standard HTML <form> submission, always ensure keyboard events (keydown Enter) are manually wired to trigger the primary action, and manage aria-busy state on buttons for async operations.

## 2026-05-29 - Async Interaction States and CSS Disabled Selectors
**Learning:** Adding a `:disabled` state to UI elements (like buttons and inputs) during async operations is critical for clear user feedback. However, existing `:hover` rules can unintentionally override the disabled visual state, making the element still appear active on hover. Additionally, transient async actions like file generation/downloads need their own loading states (e.g., `aria-busy="true"` and temporary text) to prevent users from clicking multiple times.
**Action:** When adding `:disabled` logic to frontend components, always update related CSS pseudo-classes to exclude it (e.g., `:hover:not(:disabled)`). For any async operation (including fetch calls for downloads), wrap the logic in a `try...finally` block, explicitly setting `disabled=true` and `aria-busy="true"` at the start, and guaranteeing restoration in the `finally` block.
